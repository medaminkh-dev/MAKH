# MakhOS Phase 25 (FB-1): framebuffer graphics console

**Version:** 0.1.0-dev
**License:** AGPL-3.0-only (or commercial, see LICENSING.md)
**Status:** COMPLETE — MAKH asks GRUB for a 1024×768×32 linear framebuffer and,
when it gets one, renders the console as antialiased text over a warm 16-colour
palette; with no framebuffer it falls back to 80×25 VGA text, unchanged.
**183 in-kernel tests.**
**Depends on:** 22 (higher-half MMIO window — the framebuffer is mapped there)

---

## 1. Scope

The foundation for a real graphical boot (the fennec splash + spinning loader
land on top of this in FB-2). VGA text mode gives only 16 attributes and no
pixels, so a prettier terminal needs an actual framebuffer. This brick brings one
up and routes every existing `terminal_*` call through it — no caller changes.

What it adds:

- **A framebuffer request** in the multiboot2 header (`boot/boot.asm`): a type-5
  tag asking for 1024×768×32, flagged *optional* so a firmware that can't provide
  it still boots (we fall back to VGA text).
- **A framebuffer driver** (`kernel/drivers/fb.c`, `kernel/include/drivers/fb.h`):
  maps the linear framebuffer into the higher-half MMIO window with
  `vmm_map_mmio()` (so it is reachable under any CR3, uncached), and exposes
  pixel/rect primitives plus a text console built on an antialiased 8×16 font.
- **An antialiased font** (`kernel/include/fb_font.h`, generated by
  `tools/genfont.py` from IBM Plex Mono, SIL OFL 1.1): 95 glyphs (ASCII 32–126),
  one coverage byte per pixel.
- **Console delegation** in `kernel/vga.c`: when a framebuffer is live,
  `terminal_putchar` / `terminal_newline` / `terminal_clear` and the cursor
  getters/setters delegate to the pixel console; otherwise the classic VGA-text
  path runs. The serial mirror is untouched either way.
- **Line-editor support** in `kernel/input_line.c`: the in-kernel shell's single
  -line editor renders through framebuffer cell primitives (clear-row, draw-cell,
  underline cursor) instead of poking `0xB8000`, which is not the display once a
  graphics mode is set.

### The palette

A warm, mellow 16-colour theme (`vga_rgb[]` in `fb.c`) mapped from the same VGA
colour codes the console already uses, so existing colour-coded output simply
looks richer: a soft charcoal background (not hard black), cream text, and
gentler accents. It is MAKH's own look, not a copy of any proprietary theme.

## 2. How it renders

- **Pixel packing** adapts to the framebuffer's reported channel positions
  (`fb_rgb()`), so 32bpp `XRGB` (what QEMU's std VGA gives) and other direct-RGB
  layouts both work; only direct-RGB (`framebuffer_type == 1`), 24/32 bpp are
  accepted, anything else falls back to VGA text.
- **Glyphs** are blended over the cell background with a divide-free
  `bg + ((fg-bg)*a >> 8)` alpha blend (coverage nudged `0..255 → 0..256` so full
  coverage reaches the foreground exactly). No SSE/FPU — the kernel is built
  `-mgeneral-regs-only`.
- **Scrolling** copies the text area up one 16-px row in 32-bit units (4× less
  uncached traffic than a byte `memmove`; a `memmove` fallback covers odd
  pitches) and clears the freed line to the background.

## 3. Keeping the self-tests fast and green

The headless suite (`makh.test`) asserts on the **serial** mirror, never on the
screen. `fb_init()` still runs under test (exercising the mapping and tag
parsing), but the pixel console is then switched off (`fb_console_set_enabled(0)`)
so heavy log output never pays the per-glyph / per-scroll cost. The console is
thus VGA-text during tests and framebuffer during a real boot — identical serial
output in both.

## 4. Verification

- **183 in-kernel tests pass**; `make stress` (24×4) clean.
- **Visual:** booted `makhos.iso` (in-kernel shell, real PS/2 keyboard) and a
  `makh.sh` image (userspace `/bin/sh`) headless under QEMU, captured the
  emulated display over QMP `screendump`. Both render crisply: boot log with
  cyan `[CHECK]` / green `[OK]` colour-coding, the shell prompt, typed-input echo,
  and the line editor's underline cursor — all on the framebuffer, scrolling
  cleanly. The framebuffer is confirmed at 1024×768 (the screendump is exactly
  that size).

## 5. Not in this brick (next)

- **FB-2:** the MAKH fennec logo splash + a smooth timer-driven spinning loader,
  drawn with the pixel primitives here, transitioning into the console.
- A double-buffered / damage-tracked path if tear-free scrolling under very heavy
  output is ever wanted (direct-to-framebuffer is fine for interactive use and on
  QEMU, where the framebuffer is host RAM).
- The boot visuals (fennec splash) and the fast quiet boot that lands on the
  user-space shell are a separate brick (see PHASE26); FB-1 is just the pixel
  console they draw on.
